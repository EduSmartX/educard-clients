# EduCard Mobile App — Coding Guidelines & Best Practices
# Updated: April 17, 2026
# Purpose: Enforce code quality, efficiency, reusability, and consistency

## 1. REACT PATTERNS TO FOLLOW

### 1.1 Container / Presentational Pattern
- Separate business logic from UI rendering
- Screen files (e.g., teachers.tsx) = Container (data fetching, state, handlers)
- Card/List components (e.g., TeacherCard.tsx) = Presentational (props in, JSX out)
- Presentational components should be pure — no hooks, no API calls, no side effects
- This makes components independently testable and reusable across screens

### 1.2 Custom Hooks Pattern
- ALL data fetching, mutations, and business logic must live in custom hooks
- One hook file per entity: useTeachers.ts, useStudents.ts, useClasses.ts, etc.
- Hooks encapsulate: query keys, API calls, caching config, select transforms
- Screen files should NEVER call API functions directly — always go through hooks
- Extract any logic used in 2+ places into a hook (e.g., useDebounce, useScrollDirection)

### 1.3 Compound Components Pattern
- Build complex UI from composable sub-components (e.g., FilterModal + FilterChip + ActiveFilters)
- Each sub-component handles its own rendering; the parent orchestrates composition
- Prefer this over mega-components with 10+ props and conditional rendering

### 1.4 Render Props Pattern
- Use when a component needs to share logic but the UI varies per consumer
- Example: a generic <InfiniteList> that accepts renderItem as a prop
- Prefer custom hooks over render props when logic-only sharing is needed

### 1.5 Controlled Components Pattern
- All form inputs (TextInput, Picker, Switch) must be controlled by parent state
- Never rely on internal uncontrolled state for form values
- Use single source of truth: state lives in the parent, passed down via props
- Apply to: search bars, filter modals, add/edit forms

## 2. NO HARD-CODED VALUES

### Constants
- ALL magic numbers, strings, and config values must live in shared constants
- Use `@educard/shared` package: `packages/shared/src/constants/`
- Examples:
  - Page size → `API_CONFIG.DEFAULT_PAGE_SIZE` (not `15` inline)
  - API timeout → `API_CONFIG.TIMEOUT` (not `30000` inline)
  - Storage keys → `STORAGE_KEYS.ACCESS_TOKEN` (not `'accessToken'` inline)
  - Colors → `Colors.gray[400]` (not `'#9ca3af'` inline)
  - Role gradients → `getRoleGradient('admin')` (not hardcoded array)

### Strings
- No inline error messages — define in a constants/messages file
- No inline API endpoint strings — use `API_ENDPOINTS` from shared
- No inline route paths — use defined route constants

### Rule: If a value appears in more than one file, it MUST be a shared constant

## 3. ERROR HANDLING

### API Layer
- Every API function must have try/catch with meaningful error logging
- Use a centralized error handler utility, not per-file error handling
- Log context: endpoint, params, error message, status code

### Hook Layer
- React Query handles retries and error states automatically
- Expose `isError` and `error` from hooks — never swallow errors silently
- Configure sensible defaults: retry 1-2 times, not infinite

### UI Layer
- Every list screen MUST have 3 states: Loading, Error (with retry), Empty
- Error state must show: error icon, user-friendly message, retry button
- Never show raw error messages to users (e.g., "AxiosError: Network Error")
- Use Alert.alert only for destructive confirmations, not for error display

### Global Error Boundary
- Wrap the app in an ErrorBoundary component for unhandled crashes
- Show a fallback UI with "Something went wrong" + restart option

## 4. PERFORMANCE & EFFICIENCY

### API Call Discipline
- DO NOT make API calls on every keystroke — use submit/blur triggers for search
- DO NOT let FlatList fire duplicate calls when scrolling up — use scroll direction guard
- DO NOT refetch on window focus or reconnect for list data (staleTime handles freshness)
- Use `useDebounce` for any input that triggers API calls

### Scroll Direction Guard (Required for ALL FlatList screens)
- React Native's `onEndReached` fires spuriously when scrolling UP
- Track scroll offset with `useRef`, only call `fetchNextPage` when scrolling DOWN
- Always include: `onScroll`, `scrollEventThrottle={16}`, `onEndReachedThreshold={0.5}`
- RefreshControl: `refreshing={isRefetching && !isFetchingNextPage}`

### Caching Strategy
- staleTime: 2 min (data considered fresh — no background refetch)
- gcTime: 10 min (keep in cache even when component unmounts)
- refetchOnWindowFocus: false
- refetchOnReconnect: false
- This prevents unnecessary network requests when navigating between screens

### Rendering
- Use `useCallback` for all handler functions passed as props
- Use `useMemo` for expensive computations and derived data
- Use `React.memo` for list item cards to prevent re-renders on parent state change
- FlatList: always provide `keyExtractor`, never use array index as key

## 5. REUSABILITY PRINCIPLES

### Single Responsibility
- One component = one job. If a component does fetching + rendering + filtering, split it
- One hook = one entity. Don't mix teacher and student logic in the same hook
- One API file = one entity. `api/teachers.ts`, `api/students.ts`, etc.

### DRY (Don't Repeat Yourself)
- If you copy-paste code, extract it into a shared utility, hook, or component
- Shared styles go in `@/styles/` — never redefine the same StyleSheet in multiple files
- Shared types go in `@educard/shared` package — never redefine interfaces locally

### Shared Package (`@educard/shared`)
- Types, constants, API endpoints, colors, role themes — all live here
- Used by: mobile app, web app, any future client
- When adding a new constant/type, ask: "Will another client need this?" → If yes, shared

### Component Library
- Reusable UI: `@/components/common/` (SearchBar, EmptyState, LoadingMore)
- Domain-specific: `@/components/filters/`, `@/components/cards/`
- Every reusable component must accept props — no internal hardcoded data

## 6. TYPE SAFETY

### Strict TypeScript
- No `any` type — use proper interfaces for all API responses, props, state
- Define response types that match the ACTUAL backend serializer output
- Keep types in sync with backend: if serializer changes, update the shared type
- Use discriminated unions for state (loading | error | success), not boolean flags

### Type Alignment with Backend
- Backend `ClassSimpleSerializer` returns `{ public_id, class_master_name, name }`
- Frontend types must match: `class_master_name: string` (not assume nested object)
- When backend changes a serializer, update `@educard/shared/types/` immediately
- Add fallback chains for optional fields: `field_a ?? field_b?.name ?? fallback`

## 7. CODE ORGANIZATION

### File Naming
- Hooks: `use{Entity}.ts` (e.g., useTeachers.ts)
- API: `{entity}.ts` (e.g., teachers.ts)
- Screens: `{entity}.tsx` in the route folder
- Components: PascalCase (e.g., TeacherCard.tsx, FilterModal.tsx)

### Folder Structure
```
src/
  api/           → API functions (one file per entity)
  hooks/         → Custom hooks (one file per entity)
  components/
    common/      → Reusable UI (SearchBar, EmptyState, LoadingMore)
    filters/     → Filter modals and chips
    cards/       → List item cards
  styles/        → Shared StyleSheet definitions
  utils/         → Pure utility functions (formatDate, truncateText, etc.)
```

### Import Order
1. React / React Native
2. Third-party libraries (expo-router, react-native-reanimated, etc.)
3. @educard/shared imports
4. @/ alias imports (hooks, components, styles)
5. Relative imports (./types, ./utils)

## 8. DATA DISPLAY RULES

### Names & Sorting
- All people lists (teachers, students, staff) must sort by first_name, last_name
- Pass `ordering: 'user__first_name,user__last_name'` as default in hook calls
- Display full_name, never construct "first + last" in the UI

### Class Display
- Always show: `${class_master_name} - ${section}` (e.g., "10th - B")
- Never show section alone (e.g., just "B") — meaningless without grade context
- Fallback chain: `class_master_name` → `class_master?.name` → `name`

### IDs & Codes
- Show admission numbers, employee IDs, subject codes in colored badge chips
- Never show internal UUIDs/public_ids to users

### Truncation
- Long text: `numberOfLines={1}` with ellipsis
- Card titles: max 1 line. Subtitles: max 1 line. Descriptions: max 2 lines

## 10. QUICK REFERENCE — COMMON MISTAKES TO AVOID

❌ Defining `const DEFAULT_PAGE_SIZE = 15` in every hook file
✅ Use `API_CONFIG.DEFAULT_PAGE_SIZE` from `@educard/shared`

❌ Calling API directly in a screen component
✅ Always go through a custom hook

❌ Using `any` to bypass type errors
✅ Fix the type definition to match the actual data shape

❌ FlatList without scroll direction guard → duplicate API calls
✅ Always track scroll direction with useRef

❌ Search API fires on every keystroke
✅ Trigger search on submit/blur only, or use useDebounce

❌ Showing section name alone (e.g., "B") for class
✅ Show "10th - B" using class_master_name + name

❌ Raw error messages shown to users
✅ User-friendly error UI with retry action

❌ Copy-pasting styles across screen files
✅ Use shared styles from @/styles/

❌ Hardcoded route strings scattered everywhere
✅ Use route constants from shared config

### 11.3 Shared Query Keys

ALL query keys are defined in `@educard/shared/constants/query-keys.ts`:

```ts
QueryKeys.TEACHERS = {
  ALL:       ['teachers']                        // Base key for invalidation
  LISTS:     () => ['teachers', 'list']          // All list queries
  LIST:      (params) => ['teachers', 'list', params]     // Paginated (web)
  INFINITE:  (params) => ['teachers', 'infinite', params] // Infinite scroll (mobile)
  DETAILS:   () => ['teachers', 'detail']        // All details
  DETAIL:    (id) => ['teachers', 'detail', id]  // Specific detail
}
```

Feature hooks delegate to shared keys (thin wrapper):
```ts
export const teacherKeys = {
  all:      QueryKeys.TEACHERS.ALL,
  lists:    () => QueryKeys.TEACHERS.LISTS(),
  infinite: (p?) => QueryKeys.TEACHERS.INFINITE(p as any),
  detail:   (id) => QueryKeys.TEACHERS.DETAIL(id),
};
```

### 11.5 API Function Pattern

```ts
// src/features/{entity}/api/{entity}-api.ts
import { apiClient } from '@/api/client';
import { API_ENDPOINTS } from '@educard/shared';
import type { Entity, EntityDetail, CreatePayload,
              ApiListResponse, ApiDetailResponse } from '@educard/shared';

export type EntityListResponse = ApiListResponse<Entity>;

export async function getEntities(params?): Promise<EntityListResponse> {
  const response = await apiClient.get<EntityListResponse>(
    API_ENDPOINTS.{ENTITIES}.LIST, { params }
  );
  return response.data;
}
```

### 11.6 React Query Hook Pattern

```ts
// src/features/{entity}/hooks/use-{entity}.ts
import { useInfiniteQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { QueryKeys } from '@educard/shared';
import { DEFAULT_PAGE_SIZE } from '@/api/client';

// Infinite scroll (mobile standard)
export function useEntities(params?) {
  return useInfiniteQuery({
    queryKey: entityKeys.infinite(params),
    queryFn: ({ pageParam = 1 }) => getEntities({ ...params, page: pageParam }),
    initialPageParam: 1,
    getNextPageParam: (lastPage) =>
      lastPage.pagination.has_next ? lastPage.pagination.current_page + 1 : undefined,
    select: (data) => ({
      items: data.pages.flatMap(p => p.data),
      totalCount: data.pages[0]?.pagination.count ?? 0,
      hasMore: data.pages.at(-1)?.pagination.has_next ?? false,
    }),
    staleTime: 2 * 60 * 1000,
    gcTime: 10 * 60 * 1000,
    refetchOnWindowFocus: false,
    refetchOnReconnect: false,
  });
}

// Mutation pattern
export function useCreateEntity() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (data) => createEntity(data),
    onSuccess: () => qc.invalidateQueries({ queryKey: entityKeys.all }),
  });
}
```

### 11.7 Validation & Payload Pattern

Schemas in `@educard/shared/utils/entity-form-schemas.ts`:
```ts
import { teacherFullSchema, validateField, validateAllFields } from '@educard/shared';

// onBlur
const error = validateField(teacherFullSchema, 'email', value);

// onSubmit
const errors = validateAllFields(teacherFullSchema, formValues);
```

Payloads in `@educard/shared/utils/form-helpers.ts`:
```ts
import { buildTeacherPayload, parseApiErrors } from '@educard/shared';

const payload = buildTeacherPayload(form, false);
// On error:
const { fieldErrors, generalError } = parseApiErrors(err.response?.data);
```

### 11.8 Re-Export Shim Pattern

Old flat files become shims (backward compat while migrating):
```ts
// src/api/teachers.ts
/** @deprecated Import from '@/features/teachers' instead */
export { getTeachers, createTeacher, type TeacherQueryParams } from '@/features/teachers';
```

New code must ALWAYS import from `@/features/{entity}`.

### 11.9 Adding a New Feature Module — Checklist

□ Add types to `@educard/shared/types/{entity}.ts` + export from index
□ Add query keys to `@educard/shared/constants/query-keys.ts`
□ Add Zod schema to `@educard/shared/utils/entity-form-schemas.ts` (if form)
□ Add payload builder to `@educard/shared/utils/form-helpers.ts` (if form)
□ Create `src/features/{entity}/api/{entity}-api.ts`
□ Create `src/features/{entity}/hooks/use-{entity}.ts`
□ Create `src/features/{entity}/index.ts` (barrel exports)
□ Add `export * from './{entity}'` in `src/features/index.ts`
□ Create route screens in `app/(admin-screens)/{entity}/`
□ Update `app/(admin-screens)/_layout.tsx`
□ Rebuild shared: `cd packages/shared && pnpm build`
